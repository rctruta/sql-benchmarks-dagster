# Experiments

Every experiment in this lab is one config file in, one sealed capsule out. This
page is how you run your own, and a catalog of the ones already published.

## Run your own experiment

1. **Start from the template.** Copy
   [`sql_benchmarks/experiments/templates/experiment_template.yaml`](../sql_benchmarks/experiments/templates/experiment_template.yaml)
   — it's a complete, valid experiment with every field annotated. Don't start
   from a blank file; start from that and edit.

   ```
   cp sql_benchmarks/experiments/templates/experiment_template.yaml \
      sql_benchmarks/experiments/queue/my_experiment.yaml
   ```

2. **Edit the copy.** Set the engines, the data, the SQL suite, the matrix. The
   template explains each field inline.

3. **Run it.** Anything dropped in `experiments/queue/` is picked up and run.
   The result is a **capsule** in `sql_benchmarks/experiments/results/<ID>/` —
   the flattened CSV, the raw per-replication timings, the bench conditions, your
   config archived verbatim, and an integrity seal.

## The contract

There is no external standard here — the contract is this lab's own, and it is
**enforced fail-fast**: [`sql_benchmarks/utils/schema.py`](../sql_benchmarks/utils/schema.py)
(Pydantic). A config that violates it is rejected at validation, before anything
runs. There is no partly-valid experiment.

Two properties to keep in mind:

- **Identity is content-addressed.** The Experiment ID is a SHA-256 of the parsed
  config, the SQL, and the measurement code. Change the *question* (engines, data,
  seed, suite, matrix) and the ID changes; reformat the *file* (comments, spacing)
  and it doesn't.
- **Your file is archived verbatim.** The config stored in the capsule is your
  exact bytes — comments, underscores, prose and all — not a re-serialization.
  What you write is what a reader sees.

For how a published result is verified without trusting the author, see
[published_capsules.md](published_capsules.md).
